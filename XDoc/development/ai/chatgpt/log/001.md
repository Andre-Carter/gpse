3. The areas that deserve debate
These are organizational questions, not proposed changes yet.
A. references
This is the most interesting one.

Currently:
- guides contains utilization and standards.
- reference contains general technical references.
- rust contains language-specific references.
- sources contains source catalogs.
The potential problem is that reference is both the name of a folder and the name of the larger category.

For example:

references/reference/headers.md

It is understandable, but not especially clear.

I also want to investigate whether mathematical/geometry.md belongs in general references or should eventually become a dedicated mathematical research/reference area.

No relocation proposed yet.
B. development
There is a distinction worth preserving:
- Planning describes intended work.
- Procedures describe how work is performed.
- Status describes the current state of work.
- Bugs and issues document problems.
One question is whether bugs and issues are truly separate categories or whether they describe different stages of the same problem-management process.

We should inspect their actual contents before deciding.
C. engineering
Three files:
- architecture.md
- schematics.md
- systems.md
I like this separation. But we should establish their boundaries so the same architecture decisions aren't duplicated across all three.
D. XGPSE
This one deserves special attention.

Your note says:
A MIRROR OF GPSE.

And you've proposed XMirror as a generic name that could survive a project rename.

I like the motivation. But before renaming it, we need to understand what a mirror actually contains:
- Current source-tree representation?
- Architectural documentation?
- Module and file inventories?
- Descriptions of individual systems?
- Historical snapshots?
A mirror that documents GPSE is different from a mirror that reproduces its actual directory structure.
E. x_files
We should not assign this a purpose just because the folder exists. Let's determine whether it is an archive, quarantine area, miscellaneous collection, or something else.

4. Our first organizational rules
I'd like to establish these as proposed rules for this cleanup:
1. No file is deleted during organization.
2. No file is renamed until its purpose is understood.
3. No information is discarded merely because it is duplicated; first determine which copy is authoritative.
4. Each document should have one primary home.
5. Cross-references are preferable to maintaining multiple copies of the same information.
6. Proposed architecture must remain distinguishable from approved architecture.
7. The XDoc tree must describe reality, not an imagined future structure.
These rules align with your goal of preserving lessons and making XDoc useful to the next engineer.
